# Mariachang 放置ゲーム：リファクタリング案と第1段階の実装

調査日：2026-09-30。対象：`Mamiki765/Mariachang` PR #21、`feat/hakoniwa-link-achievement`。
調査元HEAD：`65cd3c4b166205b6c4c3a1f675d351e97ae392d8`。

## 結論と今回の範囲

問題は `.mjs` そのものではなく、「進行計算」「表示用の計算」「取得・保存」「Discord操作」の責務が重なっていること。
TypeScript化、新しいフレームワーク、汎用Service/Repository階層、長寿命キャッシュは導入しない。
既存の計算を正とし、数式の適用順・丸め・保存形式を維持して、小さく共有化する。

**このコミットで実装したのは第1段階の画面制御整理。数式の一本化や保存競合対策はまだ実装していない。**
箱庭リンクコマンド、実績150「島主」、既存の4.33.1へのバージョン変更は維持する。マージ・デプロイ・DB変更は行わない。

## 実際に確認した重複と危険箇所

### 1. 同じ表示状態に対する倍率の再計算

`getSingleUserUIData` は `calculateFinalMeatEffect`、`calculateFactoryEffects`、`calculateRadianceMultiplier` を呼び、その後 `calculateProductionRate` の中で同じ種類の値を再計算する。
`generateFactoryEmbed` でも輝き倍率を計算し、アセンションのIC7・IU23・IC8・IU65・Eternity補正を組み立て直している。
このアセンション式は生産計算側にも存在する。式の変更漏れで、表示と実収益がずれる構造になっている。

**提案：生産量だけでなく内訳を返す共通の計算関数にする。**
工場効果、肉指数、輝き、スキル、アセンション、GP等の数値を1つの計算結果として扱い、UIはその結果を整形する。
共有の単位は「同じ状態・同じ時刻・同じ入力」。進行前の結果を進行後の画面に使い回さない。

### 2. 期間平均と現在値は重複ではない

オフライン進行ではGPの開始値・終了値から平均効果を求める。UIは終了時点のGP効果を表示する。
ジェネレーターも親からの生産を含めた平均所持数を使って進行させている。

**この2種類の評価を単純に1回へ削減してはいけない。**
共通関数に平均GP効果を渡す場合と現在GP効果を渡す場合を区別し、適用順、softcapの位置、IC9の工場数を保持する。
概算積分なので「時間を分割して計算しても必ず完全一致する」といった性質をテストに捏造しない。

### 3. 表示データ取得が保存も行っている

`getSingleUserUIData` は3種類の関連データを取得し、進行計算、IC6関連のUI処理、ランキング判定、`IdleGame.update`、表示用計算まで行う。
画面遷移でもこの関数が必要なため、名前だけ見て純粋な読取処理やキャッシュ可能な処理と判断してはいけない。
初回 `/idle` ではその後に実績解除や覗きバフ更新があるため、最終状態と先に計算した表示用値の整合も次段階で扱う。

**提案：進行を確定する処理と、確定済み状態から画面用データを作る処理を分ける。**
まず既存呼出元を維持できる入口を残し、中身を分離する。購入判定用の数値は操作時の最新状態から計算し、画面の見積りをそのまま購入に流用しない。

### 4. 保存経路の競合は性能問題とは別に扱う

UI側はrawデータ取得後に更新する。定期更新はrawデータのチャンク取得後に `bulkCreate(...updateOnDuplicate)` を行う。
並行操作との間で古いスナップショットを保存する競合リスクがある。これは静的読解による指摘で、本番での再現確認はしていない。
定期更新のoffsetページングには明示的なorderもない。

**提案：全ての書込み経路で同じ整合性方式を選ぶ。**
対象行ロックを使う方式と、バージョン等を条件にした更新方式を比較して決める。UIだけロックして定期bulk更新を放置しても解決しない。
この変更はDBを含む競合テスト付きの別段階にする。性能対策を理由に全件並列化したり、安易な自動再試行を追加しない。

### 5. 計算関数の入力と時刻も整理対象

`calculateOfflineProgress` は日時を内部取得し、`calculateProductionRate` もバフ判定の日時を取得する。
また、ジェネレーター配列の要素は元のJSONオブジェクトを参照しており、その `amount` を書き換える。

**提案：1回の処理に1つの `now` を渡し、更新するJSONだけ明示的にコピーする。**
全データのJSON stringify/parseコピーはしない。バフ切れを跨ぐ期間の積算方法の変更は、単なるリファクタと混ぜず仕様変更として扱う。

## 第1段階：今回実装したこと

`commands/slashs/idle.mjs` 内の小さな変更に限定した。新たな実行経路や依存パッケージはない。

- 初回描画と操作後描画の2つのswitchを、同じ `buildIdleView` と描画先Mapへ集約した。
- 画面切替では、直後の `getSingleUserUIData` と重複する事前の `IdleGame.findOne` を省いた。説明表示でもその事前参照を省いた。
- 購入・リセット等については既存の存在確認を維持した。個別ハンドラやトランザクションは変更していない。
- 操作完了後の `getSingleUserUIData` と `Point.findOne` を `Promise.all` で並行取得する。クエリ数の削減ではなく独立した待ち時間の重なりを減らす変更で、両者の原子性を保証するものではない。
- 最後に正常表示できた `uiData` を保持し、コレクター終了時に初回の人口・残高へ表示が戻る問題を修正した。終了時の工場画面表示という既存仕様は維持し、新しい進行計算や保存は追加しない。
- 再代入のない変数の `const` 化と未使用の `createdPoint` 除去を行った。

変更していないもの：生産式、丸め、コスト、報酬、実績条件、設定値、DBスキーマ、人口更新頻度、購入・リセットの処理順、モーダル処理、ランキング更新条件。
複数コレクターの並行操作や、終了と処理中の再表示が重なる問題を全面的に解決したという主張ではない。

### 次の実装順

| 段階 | 変更 | 完了の判断 |
| --- | --- | --- |
| 2 | 生産計算の内訳を共有し、UI側のアセンション等の再実装を削除 | 同じ状態・時刻で旧式と新式の結果が一致。平均と現在値の差は維持 |
| 3 | 進行・保存と表示準備を分離。計算入力を更新せず、時刻を明示 | 画面準備だけでは進行・保存せず、初回バフ等を含む表示の状態が明確 |
| 4 | UI・定期更新・操作の書込み整合性を統一 | 操作と定期更新を競合させても古い状態で巻き戻らない |
| 5 | 画面別の必要計算、Embed/ボタンの共通コスト見積り、format関数の整理 | 不要画面の計算をせず、見積りと実際の購入計算は同じ式を使う |

単なるファイル分割を先に大量に行わない。純粋な生産計算を切り出す段階でのみ、必要なら `idle-game/production.mjs` 等を追加する。
DB整合性の変更とゲームバランスの変更は、数式共有化のコミットに混ぜない。

## 元からある箱庭リンク追加の注意

`main.mjs` は `NODE_ENV !== "production"` の場合だけコマンドを登録する、という元PRの運用メモを維持する。
本番再起動だけでは `/hakoniwa` が登録されないため、マージ後には従来の開発・ローカル登録経路または `npm run register:commands` が必要。
この作業では登録・マージ・本番反映を行っていない。
